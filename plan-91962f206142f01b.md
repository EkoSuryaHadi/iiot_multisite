# IIOT Management Platform - Rencana Bertahap

Monorepo berisi 5 service Docker (Device/User Mgmt, EMQX cluster, Auth Webhook, ClickHouse, Analytics API) untuk mengelola IoT gateway multisite dan multitenant, dibangun bertahap per fase.

## Keputusan
- Monorepo, satu `docker-compose.yml` di root.
- Shared schema multitenancy (`tenant_id` di semua tabel).
- EMQX 5 OSS dengan HTTP authn/authz ke Webhook Server.
- Ingestion: EMQX Rule Engine.
  - Catatan: ClickHouse sink native hanya ada di Enterprise. Di OSS, Rule Engine memakai action **HTTP Server (webhook)**. Pilihan: (a) POST ke endpoint `/ingest` Analytics API, yang batch insert ke ClickHouse (disarankan, bisa validasi dan buffering), atau (b) POST langsung ke ClickHouse HTTP interface. Default plan: (a).

## Struktur repo
```
/
├─ docker-compose.yml, .env.example, Makefile
├─ services/
│  ├─ device-mgmt/     (FastAPI + Postgres + JWT)
│  ├─ auth-webhook/    (FastAPI ringan, authn/ACL EMQX)
│  ├─ analytics-api/   (FastAPI + clickhouse-connect)
│  ├─ emqx/            (config, bootstrap rule/authn via API)
│  └─ clickhouse/      (init SQL)
└─ docs/
```

## Konvensi topik MQTT
`t/{tenant_slug}/s/{site_slug}/d/{device_id}/telemetry|status|cmd|resp`
- Device hanya boleh publish `telemetry|status|resp` dan subscribe `cmd` pada topik miliknya.
- ACL diturunkan dari tenant, site, dan device.

## Fase
1. **Fondasi**: struktur repo, compose dasar, network, `.env`, Postgres + ClickHouse + 1 node EMQX berjalan. Healthcheck.
2. **Device & User Mgmt API**: model (Tenant, Site, User, Role, Device, DeviceCredential), Alembic migration, auth JWT (access + refresh), RBAC (superadmin, tenant_admin, operator, viewer), CRUD Tenant/Site/Device/User, provisioning kredensial device (client_id, password di-hash). Filter tenant otomatis dari JWT claim.
3. **Auth Webhook**: endpoint `POST /authn` dan `POST /authz` untuk EMQX. Lookup kredensial dan ACL (Postgres read-only atau cache Redis/in-memory + invalidasi). Skenario: device, user dashboard, service internal (superuser). Hasil `allow|deny|ignore`. Performa: cache TTL, p99 rendah.
4. **EMQX Cluster**: 3 node (core, atau 2 core + 1 replicant) dengan discovery static/DNS, load balancer (HAProxy/nginx stream) untuk 1883/8883/WS. Konfigurasi authn/authz HTTP via bootstrap script. TLS opsional (dev: self-signed).
5. **ClickHouse + Ingestion**: skema `telemetry` (MergeTree, partisi per bulan, ORDER BY (tenant_id, site_id, device_id, ts), TTL), `device_status`, materialized view agregasi 1m/1h. Rule Engine menarik `t/+/s/+/d/+/telemetry` lalu HTTP action ke `/ingest`. Endpoint `/ingest` melakukan validasi, async buffer, dan batch insert.
6. **Analytics API**: query time-series (rentang waktu, downsampling, agregasi), ringkasan per site dan tenant, status device online/offline, auth JWT sama (shared secret/JWKS), enforcement tenant. Pagination dan rate limit.
7. **Integrasi E2E**: simulator device (script Python paho-mqtt), tes alur: buat tenant, site, device, koneksi MQTT, publish, query analytics. Tes ACL negatif (lintas tenant ditolak).
8. **Hardening & Ops**: observability (Prometheus, Grafana, log terstruktur), backup, rate limit, rotasi kredensial, CI (lint, test, build image), dokumentasi.

## Urutan koding bersama
Mulai Fase 1, lalu Fase 2 (inti), Fase 3, 4, 5, 6, dan seterusnya. Tiap fase diakhiri verifikasi (`docker compose up`, pytest, uji manual).

## Verifikasi per fase
- Fase 1: semua container healthy.
- Fase 2: pytest (auth, RBAC, isolasi tenant) + Swagger.
- Fase 3: curl ke `/authn` dan `/authz`, lalu uji dengan `mosquitto_pub/sub`.
- Fase 4: matikan 1 node, klien tetap terhubung via LB.
- Fase 5-6: simulator mengirim data, query terverifikasi.

## Risiko
- Fitur ClickHouse sink EMQX hanya Enterprise, jadi pakai HTTP action.
- Beban webhook authn/authz: wajib caching.
- Isolasi tenant hanya di level aplikasi: wajib tes khusus.
- Rule Engine HTTP per-pesan bisa mahal: aktifkan batching, atau pertimbangkan ingestor MQTT bila throughput tinggi.
